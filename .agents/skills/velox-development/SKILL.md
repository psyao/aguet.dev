# Velox development

Read `vendor/psyao/velox/docs/` for the full reference.

## Installation

- `php artisan velox:install` sets up a fresh Laravel app as a Site (Admin panel provider, Page (hierarchical and orderable) and Post, Category (hierarchical) and Tag (flat) listed by Post, `primary` (depth 2) and `footer` Menus, views (the layout renders both Menus through `resources/views/velox/partials/menu.blade.php`), config, user model trait, session config, migrations, first Developer; without a terminal, as an agent runs it, it skips the Developer prompts: run `php artisan velox:make:developer` yourself, interactively). It deletes Laravel's default `public/robots.txt` (an edited one is kept, with a warning). It is safe to re-run: it never writes back starter content the Site removed (Content Types, Taxonomies, views, the 404 page), and asks before overwriting each published file it kept.
- The Entry form of a public Content Type ends with a collapsed SEO section (meta title, meta description, social image, noindex toggle), stored in `velox_entries.seo` (`$entry->seo['title']`, `['description']`, `['noindex']`), apart from `data`; set it in code with `'seo' => [...]`. The social image is an images-only Media pick stored in the `velox_entry_relations` pivot as `seo.image` (`$entry->relateMedia('seo.image', [$id])`); without one, Velox shares the first image of the Field the Content Type's `seoImageFrom()` names (null by default; a name that is not a `MediaRelation` Field of the type fails at boot). `<x-velox::seo />` in the layout's `<head>` renders `Velox::seo()`, a read-only object computed once per request (`title`, `description`, `canonical`, `noindex`, `type`, `siteName`, `image`): title = `seo.title` or `{Entry title} – {Site name}` (the Home Page: the Site name alone; the Site name is the SEO settings page's, else `APP_NAME`), description = `seo.description`, else the plain text of the Field the Content Type's `seoDescriptionFrom()` names (null by default; an unknown Field fails at boot), tags stripped, whitespace collapsed, cut on a word at 160 characters with `…`, else for the Home Page alone the SEO settings page's default description, none when empty, canonical = `$entry->url()`, `og:type` `website` for the Home Page and hierarchical Content Types, else `article`, meta robots `noindex` for a hidden Entry and on every page outside production, `og:image` (+ width/height), falling back last to the SEO settings page's default social image, from the image's `large` variant (largest variant without `large`, a GIF's own file), `twitter:card` `summary_large_image` with an image, else `summary`. On an Archive: title `{pluralLabel()} – {Site name}`; on a Term Archive: `{$term->name} – {Site name}` (not the breadcrumb); both without description, `og:image` the default social image, `og:type` `website`, canonical = the Archive's URL plus `?page=N` from page 2 (never `?page=1`); nothing editable. Velox's controllers resolve it before `render()` and `renderArchive()`, so an override reads `Velox::seo()` too. On a page Velox does not render, the component's `title` attribute (the published layout passes `View::yieldContent('title')`) gives `{title} – {Site name}` and nothing else. The SEO settings page (Admin, `/admin/seo`, `Capability::ManageSettings`, Developer-only) stores `site_name`, `description` and `image` (a Media id; a deleted one is ignored) in the `velox_settings` table under `seo`. See `docs/seo.md`.
- Velox answers `GET /robots.txt` as `text/plain`: `Disallow: /{panel path}` in production (the path of the panel `VeloxPlugin` is on, `/admin` by default; plain `Disallow:` for a panel at the root, on its own domain, or no panel with `VeloxPlugin`), `Disallow: /` otherwise, then `Sitemap: {APP_URL}/sitemap.xml`. A static `public/robots.txt` or a Site route for `/robots.txt` wins over it. See `docs/seo.md`.
- Velox answers `GET /sitemap.xml` as `application/xml`, one `urlset` built per request (no cache, no file) of absolute `loc` + `lastmod`: visible Entries of public Content Types without `seo.noindex` (`lastmod` = `updated_at`; the Home Page once, at `/`), Archives of public Content Types with a visible Entry, and Term Archives of public Taxonomies with a visible Entry of a public Content Type listing them, descendants' Entries included (`lastmod` = the latest `updated_at` of those Entries). No pagination, `priority` or `changefreq`; capped by the protocol at 50,000 URLs. A static `public/sitemap.xml` or a Site route for `/sitemap.xml` wins over it. See `docs/seo.md`.

## Content Types

- A Content Type is a class extending `Velox\Cms\ContentType`, kept in the Site (e.g. `app/ContentTypes/Recipe.php`) and listed in `config/velox.php` under `content_types`. Scaffold one with `php artisan velox:make:content-type Recipe` (`--prefix=`, `--hierarchical`, `--orderable`, `--archive`), then list it.
- Override `handle()`, `singularLabel()`, `pluralLabel()`, `titleLabel()` (the Admin's label for the title, "Title" by default), `icon()`, `prefix()`, `public()`, `model()`, `view()`, `render()`, `archive()`, `archiveView()`, `renderArchive()`, and `fields()` only when the defaults (derived from the class name) don't fit. An empty `prefix()` serves Entries at the Site root.
- `icon()` returns a Blade Icons name string (`'heroicon-o-cake'`), never a Filament enum.
- `public()` returning `false` keeps a type in the Admin but answers 404 for its Entries on the Site.
- Handles and non-empty prefixes must be unique: a duplicate fails the boot with an error naming both classes. A prefix must be lowercase slug segments (`blog/news`), or the boot fails too.
- Declare Fields with Velox Field classes (`Velox\Cms\Fields\Text::make('subtitle')`), never Filament components.
- Never name a Field after a `velox_entries` column of 1.0 (`id`, `type`, `locale`, `origin_id`, `title`, `slug`, `status`, `published_at`, `parent_id`, `created_by`, `data`, `seo`, `path`, `position`, `created_at`, `updated_at`, `deleted_at`) or `parent`, `origin`, `translations`, `children`: it fails at boot. A column added later (a generated column named after its Field, for `where`/`orderBy`) never hides the Field: `$entry->{field}` reads the Field, cast.
- Field kinds in `Velox\Cms\Fields`: `Text`, `Textarea`, `RichText` (a fixed-toolbar editor; stored in `data` as a TipTap document, never HTML; body images are Media Items by id, rendered through `<x-velox::image>`, a captioned one out of its paragraph in `<x-velox::figure>` (`<figure class="velox-figure">`, `<figcaption>`); `->blocks([Gallery::class])` offers Blocks, none by default; `->code()` offers inline code and code blocks, rendered `<code>` and `<pre><code>` without language or highlighting, off by default; an import turns HTML into its document with `$contentType->field('body')->fromHtml($html)`, null when empty: what the Field doesn't render is dropped, an `<img>` kept only with a Media id `data-id`), `Number` (`->min()`, `->max()`), `Boolean`, `Date`, `DateTime`, `Select` (`->options(['value' => 'Label'])`), `EntryRelation` (`->types(Recipe::class)`, `->multiple()`; stored in `velox_entry_relations`, not `data`, set in code with `$entry->relateEntries('field', [$id, ...])`; takes no `->default()`), `MediaRelation` (`->images()`, `->multiple()`; Media Items in `velox_entry_relations`, set in code with `$entry->relateMedia('field', [$id, ...])`; takes no `->default()`), `VideoUrl` (a YouTube watch/youtu.be/Shorts or Vimeo `vimeo.com/<id>` URL, stored as typed, any other URL refused on save; the view writes its own `<iframe>` from `VideoUrl::embedUrl($entry->video)`, the `youtube-nocookie.com` or `player.vimeo.com` player URL or null; no oEmbed, no component). All take `->label()`, `->required()`, `->default()`, `->helpText()`; the Admin form validates from them.
- A Block (content that isn't text, placed by Writers in a `RichText` body) is a class extending `Velox\Cms\Block`, kept in `app/Blocks/`, scaffolded with `php artisan velox:make:block Gallery` (class and `resources/views/blocks/gallery.blade.php`). Static methods: `id()` (stored in every node: never change it), `fields()` (any Field kind but `RichText`; stored in the node, an Entry or Media Item by id), `view()`, optional `label()`, `icon()`, `summary(array $values)` (the editor's one line after the label). The view gets each Field's value under its name, cast as `$entry->{name}` (picked Entries visible, in the current Locale); a required Field reading blank renders the Block as nothing. Media Items picked in a Block count as uses. See `docs/fields.md#blocks-in-the-body`. Velox's own `Velox\Cms\Blocks\Video` (id `velox.video`, a URL, an optional title and caption; renders `<iframe class="velox-video">` to the player, sized by the Site's CSS, in `<figure class="velox-figure">` when captioned) is offered like any Block; `velox:install` offers it on Post's `body`; override `resources/views/vendor/velox/blocks/video.blade.php` or subclass it, keeping its id.
- Renaming a Field leaves its stored values under the old name (the new name reads its default): Velox changes no stored value by itself. Move them in an ordinary Laravel migration's `up()` (`php artisan make:migration`, no `down()`) with `Velox\Cms\Fields\Migrate`: `renameField('recipe', 'cook_time', 'cooking_time')`, `removeField('recipe', 'calories')`, `alterField('recipe', 'cook_time', fn ($value) => ...)` (a kind change), `renameBlock('gallery', 'album')`, `renameBlockField('gallery', 'caption', 'legend')`, `removeBlockField(...)`, `alterBlockField(...)`. Name a Content Type by its handle and a Block by its `id()`, never by class. They rewrite every Entry (Translations, the Trash, relation picks in `velox_entry_relations` for rename/remove; Block operations in every stored rich-text document) without events or touching `updated_at`; a rename throws, moving nothing, when an Entry already holds the new name. Never hand-write JSON SQL on `velox_entries.data` (see `docs/fields.md#removing-and-renaming-fields`). `php artisan velox:fields:check` (read-only; exits non-zero on findings, so run it after `migrate` in CI or on deploy) lists undeclared values and picks, Blocks a rich-text Field no longer offers, values a kind or its options reject, required Fields left blank (in Entries and Block configurations), and Entries of an undeclared Content Type. A removed Field's values (a Content Type's or a Block's) are ignored on read and kept through every save; only a Translation drops the values of its non-translatable Fields. A Field missing from an Entry or a Block placement reads its default, and the Admin form opens with it; a value the Field's kind cannot read (text that is not a date, a rich text document in a `Text`) reads `null`, never throws.
- `hierarchical()` returning `true` lets Entries of that type nest under a parent of the same type (`parent_id`, `$entry->parent`); a parent of another type, on a flat type, or making a cycle throws a `ValidationException` on save. Nested Entries are served under their ancestors' slugs (`/services/web/seo`), and moving one moves its descendants' URLs; every old URL answers 301 to the Entry's current one (Velox writes the `velox_redirects` table; to bring a former site's URLs over, call `$entry->redirectFrom('/2010/05/03/old-slug/')`, never write the table yourself). `forceDelete()` moves an Entry's children up to its own parent.
- `orderable()` returning `true` lets Writers drag the type's Entries into a hand order (`velox_entries.position`): its Admin list, its Archive and `->ordered()` follow it; new Entries and copies go to the end. A hierarchical orderable type is ordered among siblings, arranged on its Tree page (**Arrange** on its list), read with `$entry->children` and `Entry::ofType(new Page)->visible()->tree()` (roots with `children` at every depth, one query; an Entry under a hidden parent is dropped); a re-parented Entry goes last among its new siblings. For a few Entries featured in a chosen order, use a multiple `EntryRelation` Field instead.
- Adding or changing a Content Type or Field needs no migration.
- For methods, named scopes or relations on a type's Entries, give it a model: a subclass of `Velox\Cms\Models\Entry` (e.g. `App\Models\Event`), returned by the Content Type's `model()` (default `Entry::class`). Every query loads each Entry as its type's model (public page, Home Page, Archives, Term Archives, Preview, Menus, parents, `EntryRelation` values, the Admin's pages and actions); `Event::query()` sees only that type, `Event::create()` fills `type`, `Entry::newOfType(new \App\ContentTypes\Event)` builds an unsaved one. A relation is a one-line wrapper, `return $this->relatedEntries('speakers');`, typed `MorphToMany<Entry, $this>`. Never override `getMorphClass()`, `$table` or `getForeignKey()`: they stay `Entry`'s so stored relations keep working. Keep `render(Entry $entry)`'s signature and narrow it with `/** @param Event $entry */` or `instanceof`. A `select()` without `type` loads plain Entries; listeners on `Entry`'s model events don't hear a subclass. Two types naming one model, or a `model()` that isn't `Entry` or a subclass, fail the boot. See `docs/content-types.md#entry-models`.
- To customise one Content Type's Admin (form, table, actions, pages, relation managers, widgets), subclass `Velox\Cms\Filament\Resources\Entries\EntryResource` (e.g. `App\Filament\Resources\EventResource`) and register it in the panel provider: `VeloxPlugin::make()->entryResources(['event' => EventResource::class])`. Scaffold it with `php artisan velox:make:resource Event` (`--force` to overwrite): the class recomposes the default form and table pieces, and the command prints the `entryResources` line to add; nothing else generates one. It replaces the generic Resource for that handle only and inherits its labels, icon, navigation, URL, authorisation, scoped query, pages and Entry actions (`previewAction()`, `duplicateAction()`, `trashAction()`, `homePageActions()`, `attemptChange()`). Never declare `$model`: it comes from the Content Type's `model()`. Never fork the generic Resource. Fields stay the only storage: place and tweak one with `static::contentType()->field('name')->toFilamentComponent()->...`; a value in `data` needs a declared Field. Compose the form from `EntryForm::title()`, `slug()` (a list: slug input and URL), `parent()`, `fields()` (a list), `taxonomies()` (a list), `seo()` and `sidebar()` in any layout (Tabs, Sections) instead of copying it. `sidebar()` holds the Translations panel, status, URL, parent, Terms and dates: never add `slug()[1]`, `parent()` or `taxonomies()` beside it; the generic form is a two-thirds main column (`title()`, `slug()[0]`, `fields()`, `seo()`) beside it, and without it the form shows no Translations panel; leaving a piece out loses only that input (no `slug()`: the slug follows the title until first published). Compose the table as `parent::table($table)->columns([...EntriesTable::defaultColumns(), ...])->filters([...EntriesTable::defaultFilters(), ...])` (`Velox\Cms\Filament\Resources\Entries\Tables\EntriesTable`); `parent::table()` keeps the Entry actions (a row click opens Edit, no Edit action; at most one inline action by state, the rest in a row ⋮ `ActionGroup`) and sorts a non-orderable type by `updated_at` desc unless you set `defaultSort()`; columns and filters receive the Content Type's model. Custom pages extend `ListEntries`, `CreateEntry`, `EditEntry`. An unknown handle or a class not extending `EntryResource` throws when the panel registers. Velox's navigation has two groups, Content (Content Types, Taxonomies, Media Library, Menus) and Settings (SEO, Accounts, Developers only); an Entry Resource subclass stays at its type's place in Content unless it overrides `getNavigationGroup()` / `getNavigationSort()` (Velox's sorts start at 0). Any other Resource or page of the Site lands ungrouped beside the Dashboard: join a group with `protected static string | UnitEnum | null $navigationGroup = \Velox\Cms\Filament\NavigationGroup::Content;` (or `::Settings`); alias `Filament\Navigation\NavigationGroup` in a file that imports both. See `docs/content-types.md#site-resources`.

## Taxonomies

- A Taxonomy is a class extending `Velox\Cms\Taxonomy` (e.g. `app/Taxonomies/Tag.php`), known to Velox only once a listed Content Type returns it from `taxonomies()` (`[Tag::class]`); there is no `taxonomies` key in `config/velox.php`. Several Content Types may share one. Scaffold one with `php artisan velox:make:taxonomy Genre` (`--prefix=`, `--hierarchical`), then list it and create its Archive view.
- Override `handle()`, `singularLabel()`, `pluralLabel()`, `nameLabel()` (the Admin's label for a Term's name, "Name" by default), `icon()`, `prefix()` (default: handle, never empty), `public()`, `translatable()`, `archiveView()`, `renderArchive()` only when the defaults don't fit. `single()` (at most one Term per Entry) and `required()` (at least one) hold in the Admin and in `classify()`; `hierarchical()` lets Terms nest under a parent Term of the same Taxonomy. Duplicate handles, an empty or non-slug prefix, or a prefix equal to a Content Type's or another Taxonomy's fail the boot.
- Terms are `Velox\Cms\Models\Term` rows (`taxonomy` handle, `name`, `slug`, `description`, `path`), never Entries. Leave `slug` empty to build it from the name; renaming keeps it; a taken slug in the Taxonomy, or a path taken by an Entry or Term, is suffixed (`-2`). `Term::ofTaxonomy(Tag::class)` queries one Taxonomy's Terms; `$term->taxonomy()` returns its Taxonomy or null when unlisted. In a hierarchical Taxonomy set `parent_id` (same Taxonomy, never itself or a descendant, else a `ValidationException`); the path nests (`category/recipes/vegan`) and moving or re-slugging a Term moves its subtree's paths, every old path answering 301 to the Term's current Archive (`velox_redirects` table, written by Velox; `$term->redirectFrom('/old-path/')` records a former site's path). Slugs stay unique per Taxonomy across parents. Read `$term->parent`, `$term->children` (by `position` then name), `$term->breadcrumb()` (`Recipes › Vegan`), and `Term::ofTaxonomy(Category::class)->tree()` (roots with nested `children`, one query). `$term->delete()` is permanent, moves its children up to its parent, and drops its redirects.
- Writers manage each listed Taxonomy's Terms in its own Admin navigation item (authorised by `Capability::ManageEntries`) and pick them in the Entry form, after the Fields. A hierarchical Taxonomy's Terms show as a drag-and-drop tree (`solution-forest/filament-tree`, a Velox dependency) whose moves save through each Term's `save()`; the Entry form lists them by breadcrumb in tree order, without creating Terms.
- Classify in code with `$entry->classify(Tag::class, [$term, $id])`: it replaces that Taxonomy's Terms, in order, and throws a `ValidationException` for Terms of another Taxonomy, a Taxonomy the Entry's Content Type does not list, or a broken `single()` / `required()`. Saving an Entry drops its Terms of Taxonomies its Content Type no longer lists. Read with `$entry->terms(Tag::class)` (in order) and `Entry::visible()->inTerm($term)` (the Term and its descendants, each Entry once). A trashed Entry keeps its Terms; `forceDelete()` drops them. No counts are stored on Terms.
- Each Term of a public, listed Taxonomy has an Archive at its path (`/{prefix}/{ancestors' slugs}/{slug}`): visible Entries of public Content Types listing the Taxonomy, of the Term or its descendants, newest first, 10 per page, rendered with `resources/views/velox/taxonomy/{handle}.blade.php` (or `archiveView()`), which receives `$term` and `$entries`. Override `renderArchive(Term $term, LengthAwarePaginator $entries)` for Inertia or JSON. Link with `$term->url()` (`null` when not public or unlisted). See `docs/taxonomies.md`.

## Menus

- Menus are declared in `config/velox.php` under `menus`: handle (lowercase slug) ⇒ `['label' => string, 'depth' => 1 to 3]`, depth 1 by default; anything else fails the boot. Velox declares none; there is no `menus` table, and the Menu Items of a removed handle stay in the database, unseen until it is declared again.
- A Menu Item is a `Velox\Cms\Models\MenuItem` (`menu` handle, `position`, `label`, `new_tab`) pointing to exactly one target: an Entry or a Term (`$item->target()->associate($entry)`, stored as a reference so slug and parent changes follow; label defaults to its title or name), an `archive` (a Content Type handle; label defaults to its plural label, URL from `$contentType->archiveUrl()`), or a `url` (`https://`, `http://`, `/` but not `//`, `#`, `mailto:`, `tel:` only; label required). `save()` throws a `ValidationException` keyed by field for a broken rule or an Entry in the Trash; create items in code like any model. Items nest through `parent_id` (`parent`, `children` by `position`): a parent of another Menu, the item itself or a descendant, or a depth beyond the Menu's `depth` (moved descendants included) throws on `parent_id`; deleting an item moves its children up to its parent. Deleting a Term or permanently deleting an Entry deletes the items pointing to it the same way; the Trash keeps them.
- Render navigation with `Velox::menu('primary')`, never hard-coded links to Entries: it returns the visible items in `position` order as a tree of read-only nodes (`label`, `url`, `newTab`, `children`, `isCurrent`, `inTrail`), built once per request; recurse into `children` in a partial (a Site from `velox:install` has `velox.partials.menu`; edit it rather than writing another), put `aria-current="page"` on `isCurrent` and open the dropdown on `inTrail`, never compare `request()->is()` by hand. `isCurrent` compares scheme, host and path (query string ignored; the Home Page item is current at `/`; other hosts, `#`, `mailto:`, `tel:` never). Items deeper than the Menu's current `depth` are left out. An item whose Entry is a Draft, Scheduled, in the Trash or of a non-public Content Type, or whose Archive or Term has no public URL, is hidden with its whole subtree and comes back by itself once visible. An undeclared handle throws an `InvalidArgumentException`; an empty Menu returns `[]`. See `docs/menus.md`.
- Writers build Menus on the Admin's Menus page (`/admin/menus?menu=handle`, the Menu picked from a header dropdown, gated like Entries, absent with no Menu declared): a drag-and-drop tree saved as a whole on each drop, items added and edited in a modal through `MenuItem::save()`. Seed Menus in code with the same rules; don't build another Admin screen for them.

## Rendering

- Each Content Type renders with `resources/views/velox/{handle}.blade.php` (or the view its `view()` returns), which receives `$entry`.
- `archive()` returning `true` serves an Archive at the prefix (`/articles`): visible Entries, newest first, 10 per page with `?page=`, rendered with `resources/views/velox/archive/{handle}.blade.php` (or `archiveView()`), which receives a `LengthAwarePaginator` as `$entries`. It needs a non-empty prefix, or the boot fails; no Entry can be saved at an Archive's prefix.
- To answer with something other than Blade (an Inertia page, JSON), or to hand a view more than `$entry` (the Home Page's own view: branch on `$entry->isHomePage()`, `($entry->origin ?? $entry)->isHomePage()` to catch its Translations too, else `parent::render($entry)`; see `docs/routing.md`), override `render(Entry $entry)`, and `renderArchive(LengthAwarePaginator $entries)` for an Archive; for a whole Inertia Site, override it once in an `App\ContentTypes\ContentType` base class that builds props from `fields()`. `render()` is the only way an Entry becomes a response, `renderArchive()` an Archive: never assume the Entry is saved or visible there. Velox has no Inertia dependency.
- Writers preview an Entry from its Admin edit or create page: `/admin/preview/{token}` renders the form's unsaved title, Field values, relation Field picks and Terms through `render()`, in the Site's `web` middleware group, for the signed-in Account with `ManageEntries` in the session that clicked, with `X-Robots-Tag: noindex` and `Cache-Control: no-store`. Relation Field reads and `terms()` return the unsaved picks in the Writer's order: related Entries still filtered by `visible()`, deleted Media Items absent; `url()`, `slug` and `path` stay the saved values (null before the first save), `published_at` is null for a Draft: guard it in views. `Velox::isPreview()` is true only while a preview renders (the `velox:install` layout shows a "Preview" banner with it); Menu items are never `isCurrent` there, the URL being the preview's. A Translation previews in its Locale, saved or not (`app()->getLocale()`, Terms, Menus and `Velox::locales()` there; shared Fields from the Origin). Only that Entry bypasses `visible()`: keep every other query on `visible()`, never add a preview mode to it. See `docs/preview.md`.
- Read Field values as `$entry->{field}`, cast: `RichText` to a rendered, safe `HtmlString` (print it with `{{ $entry->body }}`, never `{!! !!}`; empty when unset; `$entry->raw('body')` gives the stored document or null), `Number` to int/float, `Boolean` to bool, `Date`/`DateTime` to Carbon in the app's `timezone` (keep it UTC; set the Site's zone in `velox.display_timezone`, which the Admin uses, and print a `DateTime`, `published_at` or `created_at` with `->inDisplayTimezone()`, never a `Date`, a calendar date; see `docs/installation.md` → Timezone), `Select` to the chosen value, `EntryRelation` to the visible related Entry (or a Collection in order with `->multiple()`), `MediaRelation` to the `MediaItem` model (or a Collection in order), deleted Media Items absent, `VideoUrl` to the URL as typed; core columns are `title`, `slug`, `path`, `status`, `published_at`.
- Query Entries for the Site with `Entry::ofType(new Post)->visible()`: `visible()` hides Drafts, Scheduled Entries before their `published_at`, and trashed Entries. Never filter on `status` alone.
- Leave `slug` empty to build it from the title; each Entry stores its full `path`, unique across the Site among Entries not in the Trash, and Velox suffixes a slug whose path is taken (`-2`, `-3`) on save, so never check uniqueness yourself.
- Link to an Entry with `$entry->url()`, never by building a URL from its slug or prefix (`null` for a non-public Content Type). See `docs/routing.md`.
- Changing a Content Type's or Taxonomy's `prefix()` or `hierarchical()` leaves stored paths as they were: run `php artisan velox:paths` (on the server too, after the deploy) to recompute Entry and Term paths and redirect the old URLs; it is safe to run again. Until then the Admin warns Developers. Adding a Content Type or Taxonomy needs nothing. Adding, removing or reordering Locales goes through `velox:paths` too: it stops, listing them, while a default-Locale path starts with a Locale's code; a removed Locale's Translations stay hidden until it is declared again.
- `$entry->delete()` moves an Entry to the Trash (restorable, never emptied automatically); only `forceDelete()` removes it for good, its children moving up one level. `delete()` throws a `ValidationException` (key `parent_id`) while any child is outside the Trash, and `restore()` or `save()` while the (new) parent is in it: trash children first, restore parents first.
- Copy an Entry with `$entry->duplicate()`, never Eloquent's `replicate()` (it loses related Entries, Media and Terms): it saves a Draft "*Title* (copy)" under the same parent, authored by the current Account, with `data`, `seo`, relations and Terms, in one transaction; never the Home Page role, Menu Items, redirects or children. The Admin offers it as a Duplicate action on every Content Type (`EntryResource::duplicateAction()`), asking first on an Edit form with unsaved changes (which are never copied). The panel's unsaved-changes alert is on (`VeloxPlugin` calls `unsavedChangesAlerts()`): turn it off with `->unsavedChangesAlerts(false)` after `->plugin(...)`; on an Edit page, leave with a link or `->url()`, and follow a `refreshFormData()` outside `save()` with `rememberData()`. On a multilingual Site it copies the Origin and each Translation outside the Trash, each a Draft "(copy)" linked to the new Origin; on a Translation it copies the whole Entry and returns the copy's Translation in that Locale. An Entry model with pivot tables of its own overrides `duplicate()` to copy them (the override runs on the Origin and copies its Translations' rows itself).
- Stored `status` is only `draft` or `published`; `$entry->publicationStatus()` derives Draft, Scheduled, or Published. Scheduling needs no cron or queue.
- The Home Page (`Entry::setHomePage()`, `Entry::homePage()`) is served at `/` unless a Site route answers `/`; `$entry->url()` returns the Site root for it, and its Locale's code (`/de`) for its Translation. Trashing it, reverting it to Draft, or scheduling it throws a `ValidationException` (key `status`).
- A multilingual Site declares two or more Locales in `config/velox.php` (`'locales' => ['fr' => 'Français', 'de' => 'Deutsch']`, first = default; fewer than two = monolingual, nothing changes). A Translation is an Entry of its own: create it with `$origin->translate('de', [...])` (own title, slug, status, `published_at`, `seo`), never by setting `locale` or `origin_id` yourself; `$translation->origin` reads its Origin. Its path carries its Locale's code (`de/uber-uns`); the Home Page's Translation answers at `/de`. `visible()` keeps the Locale of the page being rendered (the default one in the Admin), so a missing or unpublished Translation answers 404, never its Origin. Velox's pages call `app()->setLocale()`; Site routes and the Admin keep `APP_LOCALE`. Fields are translatable; `->translatable(false)` keeps one on the Origin, its Translations reading it from there. A Translation takes its parent (its Origin's parent's Translation, refused with a `ValidationException` on `parent_id` while missing) and hand order from its Origin, goes to the Trash, back and away for good with it; Entry relation Fields store Origins and read the current Locale's visible Translations. A Content Type's `prefix()` may return an array per Locale code (`['fr' => 'actualites', 'de' => 'aktuelles']`, naming the default Locale; a missing Locale takes the default's): Translations and the Archive live at `/de/aktuelles`. A Term translates the same way (`$term->translate('de', ['name' => ...])`, slug unique per Taxonomy and Locale, parent and position from its Origin), a Taxonomy's `prefix()` may be an array per Locale too; Entries are classified on their Origin only, `$entry->terms()` reading the Entry's Locale's Translations of its Origin's Terms (untranslated dropped), and a Term Archive lists its Locale's Entries. A Taxonomy whose `translatable()` returns `false` (Terms that read the same in every language) keeps its Terms one value for every Locale: `terms()` returns them as classified in every Locale, `translate()` on one throws, its Admin list has no Locale UI, and it must also return `false` from `public()` or the boot fails. An Archive's SEO title and an Archive Menu Item's fallback label go through `__()` (`lang/de.json`); the Admin keeps them untranslated. Build a Locale switcher from `Velox::locales()` only, never by swapping URL prefixes by hand: plain `LocaleLink` values (`code`, `label`, `url`, `isCurrent`, `isTranslation`, false when it falls back to that Locale's Home Page), none on a monolingual Site; a Site from `velox:install` has `velox.partials.locales`, included by the layout (edit it rather than writing another; keep `lang`/`hreflang` on links and `aria-current` on the current Locale). Each Translation, Archive and Term Archive is canonical to itself; `Velox::seo()->alternates` (`hreflang` => URL, rendered by `<x-velox::seo />`) lists the page's visible Translations plus `x-default` (the default Locale's), never a Home Page fallback, none on a monolingual Site, Site route or 404; `sitemap.xml` lists every Locale's URLs with `xhtml:link` alternates. The SEO settings' `site_name` and `description` are per Locale (`['fr' => …, 'de' => …]`, a plain string = the default Locale's): the Site name falls back to the default Locale's then `APP_NAME`, the description never falls back. See `docs/locales.md`.
- Site routes always win over Velox's catch-all route, a fallback route, whenever registered: add custom pages as ordinary Laravel routes. Never declare `Route::fallback()` (the boot fails): render 404s through the exception handler. Saving an Entry at a path a Laravel route answers throws a `ValidationException` (key `slug`).

## Media

- Every uploaded file is a Media Item (`Velox\Cms\Models\MediaItem`, table `velox_media_items`), owned by no Entry. Writers and Developers upload from the Admin's Media Library; JPEG, PNG and WebP images get WebP variants at upload, in the request (upright, metadata stripped, never upscaled), on `velox.media.disk` (default `public`); the original stays on `velox.media.originals_disk` (default `local`, private).
- `MediaLibrary::upload()` is the only way in: it refuses (`ValidationException`, translated message) a file whose content type is outside `velox.media.accepted` (images JPEG/PNG/WebP/GIF, PDF, Word, Excel, PowerPoint, OpenDocument; never SVG or video), or an image over `velox.media.max_megapixels` (default 40, read from the header before any decode). GIFs and documents are served as uploaded, without variants. A stored file takes the extension of its content type, never the uploaded name's. It writes the files as it is called, outside any transaction: a rollback or `migrate:fresh` leaves them under `media/{ulid}`, so an import starting over from an empty database deletes `media/` on both disks before its first upload.
- Media Items are filed into Folders (`Velox\Cms\Models\Folder`, table `velox_folders`): nested by `parent_id`, Admin filing only (no URL, no permissions, a Media Item's path never changes), a name unique among siblings whatever the case (`ValidationException` otherwise, and for a parent that is the Folder or below it). A Media Item sits in one Folder (`$media->folder()`) or at the root (`folder_id` null). File as you upload with `MediaLibrary::upload($file, folder: $folder)`, or `$media->folder()->associate($folder)->save()`. Deleting a Folder moves its Folders and Media Items up one level. An importer creates a path one `Folder::firstOrCreate(['name' => ..., 'parent_id' => ...])` per segment, with names cased as stored: `firstOrCreate` matches exactly, `save()` refuses a sibling differing only in case. See `docs/media.md#folders`.
- Let Writers attach Media Items to an Entry with a `MediaRelation` Field; its Admin picker uploads through `MediaLibrary::upload()` too.
- Variants are named widths in `config/velox.php` under `media.variants` (`xsmall` 320, `small` 640, `medium` 1024, `large` 1600, `full` 2560). It must name at least one positive integer width, or the boot fails. Run `velox:media:regenerate` after changing variants: it rebuilds existing images' variants from their originals; the Admin warns Developers until then.
- Render images with `<x-velox::image :media="$entry->cover" sizes="..." />`, never link originals: `src` the largest variant, `srcset` every distinct variant, `width`/`height`, `alt` from the Media Item (`$media->alt()`: the current Locale's, else the default's; `alt=""` when none; an `alt` attribute overrides), `loading="lazy"` and `decoding="async"` overridable, other attributes passed through; a GIF renders its file; a document or null renders nothing. See `docs/media.md`.
- Link with `$media->url('medium')` (absolute; the largest variant not wider than asked on a small image) or `$media->url()` (the largest); an unknown name throws; `null` for an image that lost its variants, so guard it outside `<x-velox::image>`. Never link `$media->path`, the private original.
- The image driver is Laravel's `images.default` (`gd` or `imagick`): never set it from Velox code. Uploads need `fileinfo`, WebP support, `public/storage` linked (`php artisan storage:link`), and PHP/Livewire upload limits raised (see `docs/media.md`).

## Accounts

- The Site's user model implements `Velox\Cms\Contracts\Account` and uses `Velox\Cms\Concerns\IsAccount` (Filament's `FilamentUser` plus app MFA with recovery codes, stored encrypted). Only Accounts whose `role` is `developer` or `writer` get into the Admin.
- Never declare `canAccessPanel()` on the user model: it overrides `IsAccount`'s, and the Admin stops checking Roles. If another Filament panel needs its own rule, return `Role::of($this) instanceof Role` for the `admin` panel.
- Check access against a Capability, never a Role: `Gate::allows(\Velox\Cms\Capability::ManageSettings)`. Writers have `ManageEntries` only; Developers have every Capability.
- Gate a Developer-only Filament page with `canAccess()` returning `Gate::allows(Capability::ManageSettings)` (or `ManageAccounts`).
- A seeder creating an Account sets its Role with `forceFill(['role' => Role::Developer->value])`: `role` isn't fillable, so `create()`/`updateOrCreate()` silently drop it. Never make `role` fillable (mass-assigned requests could grant Developer). The user factory sets `'role' => Role::Developer->value` in `definition()` when every user is an Account (factories ignore `$fillable`), or a state where a test needs one; without it, `User::factory()` users are refused the Admin.
- Developers manage Accounts from the Admin's Accounts screen. Creating an Account with its Role writes `role`; changing an existing Account's Role goes through `Velox\Cms\AccountRules::changeRole()`, never by writing `role` directly: it refuses demoting the last Active Developer and self Role changes, and signs the Account out everywhere.
- Delete an Account through `Velox\Cms\AccountRules::delete($account, $heir, $by)`, never `$account->delete()`: it hands every Entry the Account authored, trashed ones included, to `$heir`, refuses the last Active Developer and one's own Account, and ends its sessions.
- An Account with a null `password` is Invited; `Velox\Cms\AccountStatus::of($account)` derives Invited or Active.
- Give someone access by inviting them from the Accounts screen; to re-send from code, call `Velox\Cms\AccountRules::invite($account)`. It mails a 72-hour link through the `velox-invitations` password broker; never create Accounts with a password chosen for someone.
- Never queue mail, and never make a notification `ShouldQueue`: the Site has no queue worker. Mail leaves synchronously over the Site's mailer (SMTP in `.env`).
- `VeloxPlugin` turns on Filament's password reset, profile page, email change verification, and opt-in app MFA with recovery codes: don't add them to the panel provider, and don't rebind Filament's auth notifications (Velox binds non-queued ones).
- `php artisan velox:make:developer` creates a Developer Account, or promotes an existing one and resets its password, without mail.

## Views

- Velox ships no public views or assets: `velox:install` publishes `resources/views/velox/{layout,page,post}.blade.php`, `velox/archive/post.blade.php`, `velox/taxonomy/{category,tag}.blade.php`, and `errors/404.blade.php` into the Site, and updates never overwrite them. Edit them in place.
- `velox:make:content-type` creates only the class: create `resources/views/velox/{handle}.blade.php` yourself, or point `view()` at an existing view. Likewise `velox:make:taxonomy`: create `resources/views/velox/taxonomy/{handle}.blade.php`.

## Hosting and updates

- The Site runs on shared hosting with no queue worker, cron, daemon, Redis, or Node on the server. Never add queued jobs, scheduled tasks, or a server-side asset build; do the work synchronously in the request.
- Write at runtime only to `storage/`, configured filesystem disks, and the database.
- Update with `composer update psyao/velox` then `php artisan migrate --force`; check `vendor/psyao/velox/UPGRADING.md` for extra steps. After a deploy, run `php artisan optimize`.
- Velox is installed from a private repository through a read-only GitHub token in `auth.json`; never commit `auth.json`.
- If nobody can sign in to the Admin, `php artisan velox:make:developer` creates or promotes a Developer without mail; `php artisan velox:mfa:reset {email}` turns off the MFA of an Account locked out by it.
